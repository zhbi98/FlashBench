# 框架工作原理

[README](../README.md) · **工作原理** · [平台移植](porting.md) · [使用说明](usage.md) · [问题定位](troubleshooting.md) · [接口参考](api-reference.md) · [验证与测试](testing.md)

本篇说明测试如何被拆成小步推进、三种模式各自的流程、测试数据的构成，以及框架怎样保护测试区以外的数据。了解这些之后，再按[平台移植](porting.md)接入驱动。

## 轮询推进

框架不创建线程，也不在内部等待。应用反复调用 `flash_stress_poll()`，每次调用只做一小步就返回。一步可以是读一个扇区并比较，也可以是发起一次扇区擦除，或者发起一次 `prog_size` 字节的写入。

读函数返回时数据已经读完，下一次 `poll` 可以马上做下一步。擦除和写入不同：指令发出后 Flash 进入忙状态，框架随之进入等待。等待期间的每次 `poll` 只调用一次 `busy`，Flash 仍在忙就立即返回，不再访问 Flash。忙状态结束后的那次 `poll` 才继续下一步。

```text
poll → 发起擦除 → 返回
poll → busy? 是 → 返回          （等待期间，可以让出 CPU）
poll → busy? 否 → 读回查空 → 返回
```

等待期间调用 `poll` 不会让测试前进。`flash_stress_waiting()` 返回 `true` 就表示处于这种状态，调用方可以据此让出 CPU。

由此得到两个结论。第一，测试速度由调用间隔决定，因为每次擦除和写入都至少等到下一次调用。第二，每次调用占用多久由调用方控制，因为读和比较不需要等待，可以连续做很多步。例程用时间片限制一次调用最多连续工作多久，见[每次调用做多少事](porting.md#每次调用做多少事)。

擦写函数自己等待完成的阻塞式驱动也能接入。此时没有等待状态，单次 `poll` 的耗时取决于驱动。

## 状态

`flash_stress_state()` 返回当前所处的阶段，可用于显示。三种模式经过的状态如下，方括号内的部分重复执行：

```text
ROTATE     CHECK → [ ERASE → BLANK → PROG → VERIFY ] 每轮一次 → CLEAN → DONE
READ       CHECK → [ 仅第一轮：ERASE → BLANK → PROG；READ ] 每个扇区一次 → DONE
ENDURANCE  CHECK → [ ERASE → BLANK → PROG → VERIFY ] 每个扇区一次 → DONE
```

`CHECK` 先等 Flash 空闲，再逐扇区检查测试区，不可用时进入 `ABORT`。`ERASE`、`BLANK`、`PROG`、`VERIFY` 是一次擦写循环的四步：擦除、查空、写入、读回比较。`READ` 是 READ 模式的随机读，`CLEAN` 是 ROTATE 结束前把用过的扇区擦回空白。

各状态每次 `poll` 的工作量见[接口参考](api-reference.md#状态)。

## ROTATE：读写回归

以每轮写 `wr_secs` 个扇区为例，一轮依次做：

1. 逐个擦除这 `wr_secs` 个扇区。
2. 逐个扇区读回，检查全为 `0xFF`。
3. 写入测试数据，每次调用写 `prog_size` 字节，直到写满。
4. 逐个扇区读回并与写入的数据比较，重复 `reads` 遍。

全部通过则通过计数加 1。任何一步失败则失败计数加 1，记录错误详情，然后进入下一轮。

测试区按 `wr_secs` 划分成若干位置轮流使用，分摊擦写次数；不能整除时末尾剩余的扇区不使用。`reads` 大于 1 时，在不增加擦写次数的前提下加大读取的测试量。结束时把用过的扇区和启动时发现的遗留测试数据擦回空白。

## READ：驱动通信稳定性

启动检查和 ROTATE 相同。之后一轮依次处理每个扇区：

1. 由扇区地址生成该扇区的已知数据。
2. 仅第一轮：擦除、查空、写入已知数据。
3. 做 `reads` 次随机读，每次都与已知数据比较。

出错时记录，然后继续下一个扇区。停止请求在当前扇区处理完后生效。每次运行每个扇区只擦写 1 次，相对 10 万次的寿命可以忽略。结束后保留数据，下次启动时被识别为测试数据，再写一次。

**一定要写已知数据**，是因为只读不写有两个漏洞。空白区域读到的全是 `0xFF`，Flash 完全不响应、MISO 被上拉时也会显示通过。只和"上次读到的内容"比较，又发现不了每次都错得一样的系统性错误，例如 dummy 周期配错导致整体错位。和已知数据比较，这两类问题都能发现。期望数据由扇区地址算出，不需要额外缓冲区。

**随机读针对驱动最常出错的地方**。读长度在四种里选：整个扇区、1 到 16 字节的短读、约一页长度的跨页读、任意长度。起始地址任意，目标缓冲区故意偏移 0 到 3 字节使它不对齐。分段、FIFO 边界、DMA 对齐和奇数长度的处理错误，都会在这里暴露。

**每次读都检查越界和漏填**。目标范围外放保护字节，驱动写出范围时报 `READ_OVERRUN`，例如 DMA 越界或多写一个字节。目标范围内预填期望值的反码，驱动"返回成功但没填数据"一定会被发现。

## ENDURANCE：擦写次数和寿命

一轮依次处理测试区的每个扇区：擦除、查空、写入、读回比较 `reads` 遍，一个扇区完成后再处理下一个。一轮就是每个扇区一次擦写循环，所以轮数等于擦写次数。

写入的数据在奇数轮是伪随机数，偶数轮全为 `0x00`。随机数据每轮只编程约一半的位，全 `0x00` 保证每个位都经历完整的编程和擦除，擦写次数才名副其实。

每个扇区的扇区头记录本次的擦写次数，测试结束后不擦除测试区。下次启动时从扇区头读回次数继续累计，读回的值放在 `stat.cycle_base` 中，所以断电、复位、多次分段运行都不会丢掉已经做过的次数。测试区至少要 2 个扇区：一次只擦一个扇区，断电时另一个扇区的扇区头还在。换新芯片时测试区是空白的，自动从 0 开始。

出错时不中断本轮，其余扇区照常擦写，保证各扇区次数一致。首次失败的次数记录在 `stat.first_fail` 中，同时记录出错的字节数和位数，`max_errs` 轮失败后测试自动结束。注册了 `tick` 时还会记录擦除和页编程的耗时，擦除时间随磨损变长，是寿命的早期信号。

## 测试数据

每个扇区开头是 16 字节扇区头，其余是伪随机数：

| 部分 | 长度 | 内容 |
| --- | --- | --- |
| 标记 | 7 字节 | 固定值，用来识别测试留下的数据 |
| 标签 | 1 字节 | 写入这份数据的模式 |
| 擦写次数 | 4 字节 | ENDURANCE 累计次数的来源 |
| 次数取反 | 4 字节 | 校验上一项 |
| 数据 | 其余 | 伪随机数 |

伪随机数每一轮、每个地址都不同，能发现固定数据测不出的位错误。期望数据可以随时由轮次和地址重新算出，所以缓冲区只需要一个扇区大小。

## 测试区保护

启动时先等待 Flash 空闲，不会在别的擦写还没完成时就去读。然后逐扇区检查测试区：每个扇区必须是空白的，或者带测试标记。发现别的数据时中止并报 `AREA USED`，不擦除任何内容。三种模式都做这项检查。

停止请求不会立刻打断测试，各模式的收尾方式不同：

| 模式 | 停止生效的时机 | 结束后的测试区 |
| --- | --- | --- |
| ROTATE | 跑完当前一轮 | 擦回空白 |
| READ | 读完当前扇区 | 保留已知数据 |
| ENDURANCE | 跑完当前一轮 | 保留数据和次数 |

测试中途断电后，下次启动能识别遗留的测试数据并正常继续。断电正好发生在擦除或第一页写入过程中时，那个扇区的内容无法识别，启动会以 `AREA USED` 中止。确认测试区确实空闲后，用 `force = true` 启动一次即可。

## 统计与反馈

框架记录已完成、通过和失败的轮数，测试可以跑固定轮数，也可以不限轮数一直跑到手动停止。字节流量是累计读、写、擦的字节数，用 64 位保存，只统计成功的底层调用。

擦除和编程的耗时记录次数、最小值、最大值和累计值，需要注册 `tick`。非阻塞驱动的耗时量到 `poll` 发现不忙为止，调用越密越准。

每次出错都记录类型、轮次、地址、期望值、实际值、错误字节数和位数，最近一次错误一直保留到下一次出错或重新启动。错误位数少而分散，多是存储单元磨损；整字节或成片出错，多是传输问题。每轮结束和每次出错时，框架还会通过回调通知应用，由应用决定打印还是显示。
