# 框架工作原理

本篇说明测试如何被拆成小步推进、三种模式各自的流程、测试数据的构成，以及框架怎样保护测试区以外的数据。了解这些之后，再按[平台移植](porting.md)接入驱动。

## 轮询推进

框架不创建线程，也不在内部等待。应用反复调用 `flash_stress_poll()`，每次调用只做一小步就返回：

| 一步做的事 | 是否需要等待 Flash |
| --- | --- |
| 读一个扇区并比较 | 否，读函数返回时数据已经读完 |
| 发起一次扇区擦除 | 是，指令发出后 Flash 进入忙状态 |
| 发起一次 `prog_size` 字节的写入 | 是，同上 |

发起擦除或写入后，框架进入等待：之后的每次 `poll` 只调用一次 `busy`，Flash 仍在忙就立即返回，不再访问 Flash；忙状态结束后的那次 `poll` 才继续下一步。

```text
poll → 发起擦除 → 返回
poll → busy? 是 → 返回          （等待期间，可以让出 CPU）
poll → busy? 否 → 读回查空 → 返回
```

等待期间调用 `poll` 不会让测试前进。`flash_stress_waiting()` 返回 `true` 就表示处于这种状态，调用方可以据此让出 CPU，等下一次调用再继续。因此：

- **测试速度由调用间隔决定。** 每次擦除和每次写入都至少等到下一次调用，间隔越长，测试越慢。
- **每次调用的占用时间由调用方控制。** 读和比较不需要等待，可以连续做很多步；例程用时间片限制一次调用最多连续工作多久，见[每次调用做多少事](porting.md#每次调用做多少事)。

两种驱动都能接入：

- **非阻塞驱动**：`prog` / `erase` 发完指令就返回，同时提供 `busy`。
- **阻塞驱动**：`prog` / `erase` 内部等到操作完成才返回，`busy` 填 `NULL`。此时没有等待状态，单次 `poll` 的耗时取决于驱动。

## 状态

`flash_stress_state()` 返回当前所处的阶段，可用于显示：

```text
IDLE → CHECK → ERASE → BLANK → PROG → VERIFY ─┐
         │        ↑                            │ 下一轮
         │        └────────────────────────────┘
         │      READ（READ 模式的随机读）
         ↓
       ABORT                      CLEAN → DONE
```

- **CHECK**：启动时先等 Flash 空闲，再逐扇区检查测试区，不可用则进入 ABORT。
- **ERASE → BLANK → PROG → VERIFY**：一次擦写循环，擦除、查空、写入、读回比较。
- **READ**：READ 模式的随机读。
- **CLEAN**：ROTATE 结束前把用过的扇区擦回空白。
- **DONE / ABORT**：测试结束，或测试区不可用而中止。

各状态每次 `poll` 的工作量见[接口参考](api-reference.md#状态flash_stress_state_t)。

## ROTATE：读写回归

以每轮写 `wr_secs` 个扇区为例，一轮依次做：

1. 逐个擦除这 `wr_secs` 个扇区。
2. 逐个扇区读回，检查全为 `0xFF`。
3. 写入测试数据，每次调用写 `prog_size` 字节，直到写满。
4. 逐个扇区读回并与写入的数据比较，重复 `reads` 遍。

全部通过则通过计数加 1；任何一步失败则失败计数加 1，记录错误详情，然后进入下一轮。

- **写入位置**：测试区按 `wr_secs` 划分成若干位置轮流使用，分摊擦写次数；不能整除时末尾剩余的扇区不使用。
- **读回遍数**：`reads` 大于 1 时，在不增加擦写次数的前提下加大读取的测试量。
- **结束时**：把用过的扇区和启动时发现的遗留测试数据擦回空白。

## READ：驱动通信稳定性

启动检查和 ROTATE 相同。之后一轮依次处理每个扇区：由地址生成该扇区的已知数据；第一轮先擦除 → 查空 → 写入（只此一次）；然后做 `reads` 次随机读与已知数据比较。出错时记录，然后继续下一个扇区。停止请求在当前扇区处理完后生效。

- **擦写量可以忽略**：每次运行每个扇区只擦写 1 次，相对 10 万次的寿命可以忽略。结束后保留数据，下次启动时被识别为测试数据，再写一次。
- **一定要写已知数据**：如果只读不写，空白区域读到的全是 `0xFF`，连 Flash 完全不响应、MISO 被上拉成全 `0xFF` 都会显示通过；只和"自己上次读到的内容"比较，也发现不了每次都错得一样的系统性错误（例如 dummy 周期配错导致整体错位）。和已知数据比较，这两类问题都能发现。
- **期望数据由扇区地址算出**，不需要额外缓冲区。
- **随机读**：混合了整扇区、1～16 字节的短读、约一页长度的跨页读、任意长度，起始地址任意，目标缓冲区故意 0～3 字节不对齐。这些是驱动最常出错的地方（分段、FIFO 边界、DMA 对齐、长度为奇数）。
- **越界和漏填检查**：目标范围外放保护字节，驱动写出范围（DMA 越界、多写一个字节）报 `READ_OVERRUN`；目标范围内预填期望值的反码，驱动"返回成功但没填数据"一定会被发现。

## ENDURANCE：擦写次数和寿命

一轮依次处理测试区的每个扇区：擦除 → 查空 → 写入 → 读回比较 `reads` 遍，一个扇区完成后再处理下一个。一轮就是每个扇区一次擦写循环，所以轮数 = 擦写次数。

- **写入的数据**：奇数轮是伪随机数，偶数轮全为 `0x00`。随机数据每轮只编程约一半的位；全 `0x00` 保证每个位都经历完整的编程-擦除，擦写次数才名副其实。
- **次数累计**：每个扇区开头的 16 字节记录本次的擦写次数。测试结束后**不擦除**测试区；下次启动时从扇区头读回次数继续累计（`stat.cycle_base`），断电、复位、多次分段运行不会丢掉已经做过的次数。换新芯片时测试区是空白的，自动从 0 开始。
- **出错不中断本轮**：其余扇区照常擦写，保证各扇区次数一致。记录首次失败的次数（`stat.first_fail`）、出错的字节数和位数；`max_errs` 轮失败后自动结束。
- **耗时统计**：注册了 `tick` 时记录擦除和页编程耗时（平均、最小、最大）。擦除时间随磨损变长，是寿命的早期信号。
- **至少 2 个扇区**：一次只擦一个扇区，断电时另一个扇区的扇区头还在，次数不会丢。

## 测试数据

每个扇区开头是 16 字节扇区头，其余是伪随机数：

| 部分 | 长度 | 内容 |
| --- | --- | --- |
| 标记 | 7 字节 | 固定标记，用来识别"这是测试留下的数据" |
| 标签 | 1 字节 | 写入这份数据的模式（ROTATE、READ 或 ENDURANCE） |
| 擦写次数 | 4 字节 | ENDURANCE 累计次数的来源 |
| 次数取反 | 4 字节 | 校验上一项 |
| 数据 | 其余 | 伪随机数，每一轮、每个地址都不同 |

伪随机数据能发现固定数据测不出的位错误。期望数据可以随时由轮次和地址重新算出，所以缓冲区只需要一个扇区大小。

## 测试区保护

- **启动前检查**：每个扇区必须是空白的，或者带测试标记，否则中止并报 `AREA USED`，不擦除任何内容，避免误擦有用的数据。三种模式都做这项检查。
- **启动时先等待 Flash 空闲**：不会在别的擦写还没完成时就去读。
- **结束后恢复**：ROTATE 把用过的扇区和遗留的测试数据恢复为空白；READ 和 ENDURANCE 保留数据。
- **断电恢复**：测试中途断电后，下次启动能识别遗留的测试数据并正常继续。断电正好发生在擦除或第一页写入过程中时，那个扇区的内容无法识别，启动会以 `AREA USED` 中止；确认测试区确实空闲后，用 `force = true` 启动一次即可。
- **停止**：可随时请求停止。ROTATE 和 ENDURANCE 跑完当前这一轮，READ 读完当前扇区；ROTATE 还会把测试区擦回空白。

## 统计与反馈

- **轮数**：已完成、通过、失败的轮数。可以跑固定轮数，也可以不限轮数一直跑到手动停止。
- **字节流量**：累计读取、写入、擦除的字节数（64 位，不会溢出），只统计成功的底层调用。
- **耗时**：擦除和编程的次数、最小、最大和累计耗时，需要注册 `tick`。非阻塞驱动的耗时量到 `poll` 发现不忙为止，调用越密越准。
- **错误详情**：类型、轮次、第一个出错字节的地址、期望值、实际值、出错字节数和位数。最近一次错误一直保留到下一次出错或重新启动。位数少而分散多是存储单元磨损，整字节或成片出错多是传输问题。
- **回调**：每轮结束和每次出错都有回调通知，由使用方决定打印还是显示。
